# Phase 1 — Discovery and schema mapping

**Milestone:** M1 — Schema mapping complete  
**Scope reference:** `Teszt-Projekt-MCP.md` → “Phase 1: Discovery and schema mapping”  
**Companion overview:** `Teszt-Projekt-MCP-Implementation-Plan.md` (not modified by this file)  
**API reference:** `MiniCRM-Integrations-Manual.md`

This document is a **standalone, detailed runbook** for Phase 1 only. Complete items in order unless marked optional.

---

## 1. Purpose of Phase 1

- Understand the **real** miniCRM tenant (modules, statuses, custom fields, naming).  
- **Prove** REST API access with the real **SystemId** and **API key** on all endpoints the 12 tools will use.  
- Lock **input/output schemas** for each of the **12 MCP tools** based on **actual JSON** responses (not assumptions).  
- Document **business language** (how the client names modules and statuses) for later system prompts.  
- Produce **Deliverable 0** (schema discovery document) and get **client sign-off** (**gate M1**).  
- Create a minimal **Node.js + MCP SDK** project **stub** only (no full tool implementation — that is Phase 2).

## 6. Step-by-step work instructions

### Step 1 — Kick-off meeting (30–60 minutes)

**Before the meeting:** Send agenda: goals of Phase 1, M1 gate, no delete tools, Hungarian UX, single-user scope.

**During the meeting, capture:**

1. Confirm **Professional + REST API add-on**.  
2. Confirm **one** primary miniCRM user context for prompts (single-user project).  
3. Agree **where raw JSON samples** may be stored (client policy, PII redaction rules).  
4. Schedule **M1 review** date/time.  
5. Name a **single approver** for Deliverable 0.

**Output:** Short meeting notes (date, attendees, decisions).

---

### Step 2 — Inventory miniCRM structure from the UI

**Goal:** A human-readable map that matches what users say in Hungarian.

**2.1 — List products (modules)**  
- In miniCRM sidebar, list each product name.  
- For each, record **CategoryId** from the URL when you open that module (see Integrations Manual “Product (module/category)”).

**2.2 — Status model per module**  
- For each relevant module, list **status names** users care about (e.g. pipelines).  
- You will later attach **StatusId** numbers from Schema API — leave a column empty until Step 4.

**2.3 — Custom fields**  
- Open **field configuration** (admin) for **Contact** and **Project** cards.  
- Record **registered field names** (the part after `Contact.` or `Project.` per manual).  
- Note which fields are **required** when creating a card in key statuses (manual: required fields depend on module/status).

**2.4 — Business vocabulary**  
- Write a short glossary: UI label → user slang (e.g. “Sales” module called “értékesítés” in chat).  
- This feeds Phase 3 system prompt.

**Output:** `crm-structure-map.md` (or equivalent) with tables for modules, statuses (names), fields, glossary.

---

### Step 3 — Prepare API testing environment

**3.1 — Set environment variables locally (terminal session)**  

Example (do not commit real values):

```bash
export SystemId=YOUR_SYSTEM_ID
export ApiKey=YOUR_API_KEY
```

On Windows PowerShell, use `$env:SystemId="..."` and `$env:ApiKey="..."`.

**3.2 — Baseline connectivity test**

```bash
curl -s --user "$SystemId:$ApiKey" "https://r3.minicrm.hu/Api/R3/Category"
```

Expect HTTP **200** and JSON. If **404**, check manual: wrong credentials vs wrong URL vs subscription (Integrations Manual “Error codes”).

**3.3 — Document your HTTP client choice**  
Record in the discovery doc: curl version, Postman collection name, etc.

---

### Step 4 — Execute structured API smoke tests (save raw responses)

For **each** call below: record **request URL**, **method**, **HTTP status**, **response body** (file), and **one-line observation**.

**4.1 — Category list**  
- `GET https://r3.minicrm.hu/Api/R3/Category`  
- Validates modules and gives id → name map.

**4.2 — Schema reads (per relevant CategoryId)**  
- `GET https://r3.minicrm.hu/Api/R3/Schema/Project/{CategoryId}`  
- Repeat for **each** module you will support in natural language (at minimum those touched by pilot scenarios).  
- Optionally: `GET .../Schema/Business`, `.../Schema/Person` if contacts/companies use critical enums.

**4.3 — Contact searches**  
- `GET .../Api/R3/Contact?Name=...` (partial name allowed per manual)  
- `GET .../Contact?Email=...`  
- `GET .../Contact?Phone=...`  
- If applicable: `UpdatedSince`, `Query`, custom field as query param (manual “Search based on a specific field”).

**4.4 — Contact detail**  
- Pick one **Person** and one **Business** id from search results.  
- `GET .../Api/R3/Contact/{Id}`  
- Save full payload — defines fields for `kontakt_lekeres` / `kontakt_modositas`.

**4.5 — Project search and pagination**  
- `GET .../Api/R3/Project?CategoryId={id}`  
- Note `Count`, `Results`, `Url` on each row.  
- Test `Page=0` and `Page=1` if `Count > 100` (manual: 100 per page, page index starts at 0).

**4.6 — Project detail**  
- `GET .../Api/R3/Project/{CardId}`  
- Save JSON — defines `projekt_lekeres` shape.

**4.7 — ToDo list**  
- Use a real **CardId** (project id) that has tasks.  
- `GET .../Api/R3/ToDoList/{CardId}`  
- Optional: `?Status=Open` / `Closed` / `All`.

**4.8 — ToDo create method verification (critical)**  
The Integrations Manual labels create as **POST** but shows a **curl -XPUT** example in places. **You must determine what your tenant accepts.**

- Attempt create in a **safe** context (test env or a disposable test card).  
- Document the **working** method + body shape.  
- Save successful request/response for Phase 2.

**4.9 — Invoice read**  
- `GET https://r3.minicrm.hu/Api/Invoice` with query parameters you need (e.g. by `ProjectId` or `ContactId` per your scope and manual).  
- Note: Invoice list/detail paths and parameters — align with `MiniCRM-Integrations-Manual.md` Invoice chapter.  
- Save one successful response for `szamla_lekerdezes` design.

**4.10 — Optional exploratory calls**  
If future prompts need them: `ProjectHistory` for status history, filters on `UpdatedSince`/`UpdatedAt` for projects (manual “Search based on the update time”).

**Output:** Folder `api-samples/` with JSON files + `api-test-log.md` listing each test and result.

### Step 6 — Define the 12 MCP tool contracts

Create `mcp-tool-contracts.md` (or one section per tool in Deliverable 0).

For **each** tool below, specify in **one dedicated subsection**:

| Subsection content | Detail |
|--------------------|--------|
| **Tool name** | Exact identifier (e.g. `kontakt_kereses`) |
| **User-facing description (HU)** | Short text for MCP tool metadata |
| **miniCRM operation** | HTTP method + path + query/body |
| **Inputs** | Name, type, required?, validation, default |
| **Outputs** | JSON/text shape returned to Claude (field names stable) |
| **Errors** | Map 400, 404, 405, 429, 500 to Hungarian user messages |
| **Pagination** | If applicable: how `Page` and `Count` are exposed |
| **Rate-limit behaviour** | e.g. “this tool may issue N calls internally” (usually 1) |

**Tool list (must all appear):**

1. `kontakt_kereses`  
2. `kontakt_lekeres`  
3. `kontakt_letrehozas`  
4. `kontakt_modositas`  
5. `projekt_kereses`  
6. `projekt_lekeres`  
7. `projekt_letrehozas`  
8. `projekt_statusz_valtas` (status **only**)  
9. `teendo_letrehozas`  
10. `teendo_lekeres`  
11. `szamla_lekerdezes`  
12. `schema_lekerdezes` (define how `Category` + `Schema/{Type}` are combined in one logical tool)

**Explicit exclusion:** No DELETE / purge tools (scope).

### Step 8 — Technical design note (1–3 pages)

Create `technical-design-phase1.md` covering:

1. **Repository layout** (planned): `src/`, `tests/`, `docs/`.  
2. **Configuration:** planned `.env` variable names (no secrets in file).  
3. **Logging:** what is logged vs forbidden (no API keys, minimise PII).  
4. **Rate limiting design:** 60 req/min global per Integrations Manual; strategy (token bucket / sliding window); behaviour on **429**.  
5. **Burst control:** max concurrent outbound requests if Claude chains tools.  
6. **MCP SDK:** package name and minimal architecture (stdio server, tool registration loop).  
7. **Testing strategy preview:** unit tests with mocks in Phase 2.

## 9. Common pitfalls

- Assuming manual examples match **your** tenant’s required fields on **Project** create.  
- Ignoring **429** and pagination — will break pilot under load.  
- Starting Phase 2 coding **before** M1 — scope explicitly defers implementation.  
- Committing **API keys** — use `.env` + `.gitignore` from Phase 2 onward; Phase 1 samples should avoid secrets in shared docs.
